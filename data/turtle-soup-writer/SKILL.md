# 海龟汤创作

创作让人想追问、能逐步推理、揭晓后重新理解前文的海龟汤。先读完整参考，再设计故事与反转，最后交付七字段 JSON。

## 用户偏好与任务范围

- 默认简体中文。题材偏恐怖、悬疑、架空及生活中少见的处境，重视故事性、紧张感和揭晓后的冲击。日常场景也可以使用，但应有足够强的隐藏事件或后果。
- 汤面要像有人在讲一件怪事：语言直接、动作具体、对白自然。避免考题口吻、僵硬措辞、条件堆砌、空泛渲染及多余解释。
- 本格与变格均可，按故事成立所需的规则选择；没有指定时不预设比例。恐怖不要求每篇死人，也不靠不断加重血腥程度维持吸引力。
- 用户当次指定的数量、类别、题材、尺度和输出位置优先。未指定数量时写一篇；批量任务按约定完成，内部工作分批进行，无需逐批请求批准。
- 新作默认执行参考检索；用户给足原文、只要求润色或检查时，直接处理现有文本，仅补查必要事实。创作、文件写入、发布分别按本次授权范围执行。

## 1. 先确认真正读到了什么

优先查用户提供的具体作品或博主，其次在小红书、抖音、YouTube、哔哩哔哩及中英文创作者页面找相近题材。入口用于找到具体作品，选材仍要看完整内容和评价。英文资料同样要匹配用户要的故事体验，不能因为容易读取，就用普通逻辑小题填满恐怖故事的参考库。

对准备使用的参考，区分四种访问状态：

| 状态 | 可据此做什么 |
| --- | --- |
| 完整内容 | 已读到汤面、汤底及决定推理的规则；可以拆解、参考改写 |
| 部分内容 | 只读到片段、汤面或部分讲解；可以继续找原文，不能自行补出作者的答案 |
| 仅元信息 | 只有标题、简介、目录、播放数据或评论；可以发现候选，不能声称看过作品 |
| 无法访问 | 页面、正文或视频无法取得；明确说明具体缺口 |

视频可通过实际观看，或覆盖完整作品的字幕、转写、作者图文版本理解。先确认文字确实覆盖结局；涉及画面、音效、道具等关键线索时，还需核对对应内容。记录链接及有关时间段或段落，区分原作者、节目发布者、转载者。

遇到访问限制，当时就简短说明读到了哪些内容、还缺什么。可找同一作品的作者文字版或可靠完整转写，保留来源链。用户锁定的原作仍读不全时，请求所缺内容或询问替代参考方向，继续不依赖原作的工作；不要据元信息完成改编并宣称已满足指定参考。用户只把链接作为建议时，可继续选择题材匹配、完整可读的作品，并如实说明最终用了哪些参考。

### 选出值得参考的作品

自行检索参考时，先选中内容完整、好评有据且题材匹配的作品，再开始依赖它的改写。暂时找不到时说明缺口，继续有针对性地寻找，不把未核验的候选写成已选参考。用户指定原作或提供全文时按指定范围处理，评价不足如实记录。

- 同时考察故事吸引力、反转回收线索的能力和可推理性。惊悚标签或离奇结局本身不足以说明质量。
- 好评依据优先采用针对这篇作品的具体玩家评价、带人数的评分或可查获奖记录。记录负面反馈中的逻辑漏洞、猜设定和主持困难。
- 播放量、合集点赞和博主名气只能反映传播情况；作者自荐单独标明。票数、评分、观看范围都按实际证据描述。
- 用简短记录保留作品名、作者或发布者、链接、访问状态、评价依据、准备借鉴的具体手法。开始写作前，向用户简要交代选中的完整参考及依据。
- 少量匹配的完整样本足以启动单篇创作；批量创作应补充不同题材和推理机制的完整参考，避免把一两个短谜题反复换皮。无需为增加来源数量继续搜集同类材料。

## 2. 先写真实故事，再藏住关键联系

创作或重写时，阅读 [编辑与审稿指南](references/editorial-review.md)，用其中的方法检查草稿。

先按时间顺序写出真实发生的事，明确人物想要什么、面临什么威胁、为什么采取关键行动，以及行动造成的后果。故事的危险或损失应影响人物选择；仅有一个小误会和突然报出答案，通常达不到本技能默认的故事要求。

随后确定这条反转链：**读者最初会如何理解 → 哪个细节支持追问 → 发现什么关键联系 → 前文的动作和后果如何被重新解释。**

改编需重新安排人物处境、冲突、证据及后果，并核对改变后的因果关系。只换姓名、地点或物品名称不算完成实质改编。借鉴了具体作品的机制时保留对应来源，避免照搬独特措辞、大段剧情或把改编宣称为完全独立原创。来源说明留在作品之外。

## 3. 让反转可以推到

以下采用本题库的分类口径：

| 类别 | 规则基础 | 必须检查的内容 |
| --- | --- | --- |
| 本格 | 现实规律与可信的人物行为 | 机关、空间、职业知识和生理事实成立；拿不准的关键事实查可靠来源 |
| 变格 | 允许鬼魂、架空科技、时间循环等设定 | 核心规则的触发条件、对象、代价与限制明确，前后统一，并有可追问的现象 |

- 围绕主要反转组织线索。追加反转应继续解释已有细节，推进危险或改变人物关系；突然宣布另一条规则会削弱前面的推理。
- 汤面陈述的事实必须成立。人物误判用他的所见、所想或对白承载；叙述者的身份可以留作谜点，视角和指代仍需稳定。
- 让关键背景、人物关系或特殊规则有提问入口。必要事实可以通过问答和提示逐步取得，不能把解谜变成猜作者临时设定。
- 变格优先用少量核心规则推出后果。若解释一个漏洞就得新增一项能力或豁免条件，返回故事设计，删改因果关系。
- 人物只依据当时已知的信息行动。怀疑与确认分开，故事需要确定结论时提供相应证据。

## 4. 写成可以直接游玩的文本

**标题 `title`：** 简短、有辨识度，呼应意象或事件，保留发现核心身份和机制的空间。

**汤面 `story`：** 通常两至五句，先让读者看见一个处境，再出现值得追问的动作、细节或后果。句数服从节奏和必要线索，不做硬性字数题。恐怖感尽量落在声音、动作、物件或关系变化上。避免机械使用“为什么”“请推理”，也不在末尾罗列“没有下毒”“没有撒谎”等排除说明；真正必要的限定尽量融入情节。每句话应承担叙事、伏笔或必要限定的作用。

**汤底 `answer`：** 用连贯叙述讲清真实事件，解释汤面每个主要异常，并写全主持判定需要的规则。删除为遮掩漏洞追加的巧合、无作用的背景和替读者总结震撼感的句子。不要把审稿过程、作者意图或改稿说明写进成品。

**提示 `hints`：** 恰好三条，每条都能从汤底得到支持，逐条新增信息：①打开正确方向；②连起关键关系或规则；③接近核心解答。提示可以帮助发现背景，但不能成为给单薄汤面补写整套故事的地方。

**难度 `difficulty`：** `easy`（简单）对应一个主要误解、入口明显；`medium`（中等）需要连接多个事实；`hard`（困难）需要组合多段有线索支持的推理。设定繁多、专业知识冷僻、信息缺失都不自动构成高难度。

## 5. 审稿后再计为成稿

按[编辑与审稿指南](references/editorial-review.md)实际回读作品，分别检查：

1. **故事与语言：** 汤面能引发具体追问，人物处境有分量，读起来像叙事；删掉旁白评价后仍有吸引力。
2. **反转与逻辑：** 从汤底倒查汤面、从汤面模拟关键问答，能抵达核心答案；重要替代解释有区分线索，人物行动和规则前后一致。
3. **格式与交付：** 数量、字段、取值、三条提示及标识符合约定。

三项分别成立才交付。格式校验只能证明数据结构；编辑自检不能冒充真实玩家试玩。若用户要求评分，说明依据和具体问题，避免用自给高分作为完成证明。

批量时，对每篇保留简短的参考与检查记录，可用工作表或内部笔记。每条应能说明来源使用范围、核心误解、关键证据及提问路径；修复后重新核对受影响的汤面、汤底和提示。检查本批与旧库的具体反转机制，控制相同因果结构、结尾和句式的重复；字符串不重复不足以证明内容有区别。

按能够认真回读的批次推进，不把尚有已知矛盾、缺少来源核验或仅完成格式检查的草稿计入成稿。尚未达到约定数量或必要参考要求时，如实说明缺口，继续完成已获授权的工作。不要用减小数量、降低题材要求或替换交付方式来凑成完成状态。

## 6. 按约定交付并收尾

输出前读取 [JSON 字段规则](references/output.schema.json)，使用标准解析器或成熟校验工具检查实际成品。字段及顺序固定为：

| 字段 | 内容 |
| --- | --- |
| `id` | 小写英文字母、数字和连字符组成的唯一标识；修订原条目时保留 |
| `title` | 非空中文标题 |
| `category` | `本格` 或 `变格` |
| `story` | 非空汤面 |
| `answer` | 非空汤底 |
| `hints` | 恰好三个非空字符串，递进排列 |
| `difficulty` | `easy`、`medium` 或 `hard` |

- 直接在对话中交付作品时，单篇用对象，多篇用数组，只输出 JSON 正文，不加代码围栏或写作块。字段外不添加来源、评分或创作说明。
- 用户要求文件时，保存相同结构的 JSON，最终简短给出文件链接。来源记录按任务需要单独保存，清楚区分完整参考与只读片段。必要的访问缺口在写作前说明，不能到交付后才揭示。
- 写入已有题库前先读现有记录和配套约定，核对标识、顺序及重复内容，保持授权范围外的内容完整。未指定时不要擅自发布或导入线上。
- 完成并验证最终文件后，清理本轮临时脚本、分批草稿和抓取缓存，保留正式作品及有用的来源记录。结束说明只报告实际完成和验证的范围。
