# 决策记录、实施前置条件与资料

更新：2026-09-26。本文区分用户已确认规则、架构默认方案和外部待办。待办不影响先开发独立模块，涉及真实通道的功能必须在验证后才能声称可用。

## 1. 用户已确认

| 决策 | 最终规则 |
| --- | --- |
| 用户市场 | 中国大陆优先，后续微信生态 |
| 部署 | 前后端和数据库在国内自有服务器 |
| 客户端 | 浏览器首发，后续小程序与 App |
| 单人 | 对所有人永久免费无限；不保存服务端对话，记录在本地浏览器 |
| 多人 | 房间内共同游玩，Jev 主持，服务端保存并同步对话 |
| 未赞助用户 | 每账号累计可创建 10 个多人房间 |
| 月度赞助 | 6 元/月，有效期内不限创建房间次数 |
| 永久赞助 | 20 元，永久不限创建房间次数 |
| 登录 | 邮箱验证码 + Google 账号授权 |
| 核心系统 | 题库、Jev 可用性与判题逻辑、多人同步、UGC、完整后台 |
| 当前支付条件 | 尚无微信或支付宝商户资质 |

## 2. 架构默认决策

| 编号 | 决策 | 实际影响 |
| --- | --- | --- |
| D01 | React + Vite 玩家端与独立 NestJS 后端 | 保留 React，重建 Next 路由；单服务器可分别更新前后端 |
| D02 | 模块化单体 + 独立任务进程 | 首发无需拆微服务；模型调用慢不会占住多人写入事务 |
| D03 | PostgreSQL + pg-boss | 业务和任务可同事务提交；一个数据库完成持久化，降低运维组件数量 |
| D04 | HTTP 写入 + 标准 WebSocket 通知 + 持久事件补齐 | 协议可被小程序和 App 接入；重连与去重是业务明确承担的职责 |
| D05 | 每房单队列，一条问题一条正式判定 | 所有人顺序一致；单个慢请求会延后该房其他问题，因此设置超时和队列上限 |
| D06 | 单人使用无对话存储接口与 IndexedDB | 保留匿名和本地隐私；丢失响应需本地重试，服务端无法找回单人历史 |
| D07 | 每账号一次开房按 roomId 计，同房间换题免费 | 符合按房间收费；不会把一次朋友聚会拆成多次扣款 |
| D08 | 房间创建预留，首次有效判定才消费 | 空房取消不浪费免费机会；需要数据库事务保护预留和释放 |
| D09 | 赞助在创建房间时确认，已有房间到期后可继续 | 避免聚会被打断；下一次创建新房间再检查资格 |
| D10 | 主动付款续期；一个自然月；永久完整 20 元 | 无自动扣款任务；提前续期有清晰时间区间，购买永久前展示价格 |
| D11 | 公开投稿都经过人工批准与权利确认 | 首发内容质量可控，运营需要承担审核时间 |
| D12 | React-admin 社区版，服务端角色权限 | 标准后台列表可以快速开发；游戏、退款等动作保留业务审核 |
| D13 | 同域名部署网页/API，延续原站域名 | 网页会话更简单，旧浏览器本地记录可继续访问 |
| D14 | 初始最多 8 人/房，每人一个待处理问题 | 首发界面和主持等待较易控制；属于并发容量参数，无累计商业额度 |

这些方案可以在实施中基于明确证据调整，但不能改变已确认价格、单人隐私和无限游玩等产品规则。新增商业限制或改变永久权益必须回到负责人决定。

## 4. 不需要现在引入的复杂度

- 首发无需 Redis、消息中间件集群、服务网格或 Kubernetes。若真实负载证明 PostgreSQL 通知和单机进程不能满足目标，再增加对应基础设施。
- 不统一所有端的 UI。共享领域规则、接口、状态枚举和设计变量，后续按小程序/App 的组件与支付要求实现界面。
- 不先开发推荐模型和作者结算。先让人工审核、内容版本与真实评测数据形成稳定内容供给。
- 不为单人建立云端“匿名账号”。单人调用保持无身份，服务器不维护可关联个人的会话档案。
