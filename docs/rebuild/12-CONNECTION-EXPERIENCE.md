# WebSocket 连接与可靠发送设计

更新：2026-09-29。用户已确认继续使用 WebSocket（双向长连接）；本次设计覆盖多人消息发送确认、去重、自动重连、遗漏补齐和页面状态保留。本文涉及连接与发送体验的规则优先于旧文档。以下参数为首发默认值，功能尚待实现与实测。

## 1. 产品要求

- 玩家点击发送，立即看到自己的消息及“发送中”；只有服务端完成持久化后才能显示“已发送”。模型仍在排队或判断时，消息保持已发送，单独展示 Jev 的处理状态。
- 同一条消息网络重试始终使用同一请求编号，只生成一条正式消息。断线恢复按最后连续收到的事件编号继续。
- 短暂断线保留已加载记录、当前题目、成员列表、输入草稿、所在页签和阅读位置；恢复过程在原页面完成。
- 页面重新可见或网络恢复时立即检查连接并补齐。全员离线不会结束、归档房间或转让房主，遵循一房一题的生命周期。
- 本期仍采用 HTTP（普通请求）提交命令、WebSocket 接收事件。单人请求与本地隐私规则维持独立。

## 2. 发送状态与服务端确认

| 状态 | 页面表现 | 含义及下一步 |
| --- | --- | --- |
| sending（发送中） | 本人消息占位卡，显示“发送中” | HTTP 请求已经发起，尚无持久化证明 |
| confirming（确认中） | 原卡显示“正在确认发送结果” | 请求超时或连接中断，服务器可能已经保存；恢复后先查询结果 |
| sent（已发送） | 原卡转为正式消息 | 收到事务提交后的命令响应，或收到与请求编号对应的持久事件 |
| rejected（未发送） | 原卡显示具体原因及重试或修改入口 | 服务端明确拒绝，如无权限、房间结束、输入不合法 |

“已发送”表示平台已保存，首发不引入其他玩家已读回执。判题状态独立为排队、处理中、完成、失败、取消；模型失败不会把已保存的问题变成未发送。

发送前生成 `clientRequestId`（请求编号），冻结该次发送的 roomId、roundId、类型和正文，并保存本地待确认项。立即展示本人占位卡；成功确认后将它合并为同一张正式卡，不能追加第二张。请求期间保留原草稿；确认后仅在当前草稿仍等于发送时文本的情况下清空，不能删掉玩家刚输入的新内容。

HTTP 默认等待确认 10 秒，超时进入 confirming；终止浏览器请求不代表服务端事务已撤销。查到已受理就合并正式消息；尚未查到且房间仍可写时，最多自动重投一次相同请求，之后保留人工“继续确认”入口。断线期间不创建新的离线发送队列，允许编辑和复制草稿。多人每人最多一个未完成判题任务的规则保持有效。

已明确失败的模型任务需用户重新提问时，生成新的请求编号；网络不确定的同一次发送保持原编号。修改已被明确拒绝的正文后发送，也使用新编号。

## 3. 编号与事务契约

| 编号 | 职责 |
| --- | --- |
| clientRequestId | 标识一次用户操作；网络重试复用；同用户、同编号、不同内容返回冲突 |
| turnId / discussionId | 标识正式问题或讨论；讨论可复用创建事件的 eventId，契约须统一 |
| eventId | 标识一条持久事件 |
| seq | 房间内连续递增序号，决定事件应用顺序与补齐起点 |

服务端在同一事务保存命令结果、问答或讨论、事件及必要的任务和权益变化，事务提交后再回应“已受理”。数据库唯一约束处理并发重复请求；不能只靠前端禁用按钮。响应与事件任一先到，都通过同一请求编号合并。命令重放仍检查账号与本房阅读权限，不向被踢用户返回私有结果。

新增本人命令查询接口：`GET /rooms/:roomId/commands/:clientRequestId`，返回 accepted（已受理）及原响应或 not_found（尚未查到）。not_found 不能证明仍在传输中的旧请求永远不会提交；随后只允许用原编号重投。响应禁止公共缓存，禁止查询其他人的请求。

命令响应包含 clientRequestId、持久对象编号、acceptedSeq（对应受理事件序号）与 controlVersion（控制版本）。问答受理和讨论创建事件带 clientRequestId，供发送者合并卡片。原有快照和查询结果提供已加载消息的对应编号。收到 HTTP 确认只能标记该消息已发送，不能直接把最后连续事件序号跳到 acceptedSeq。

房主揭晓、关闭、迁移房间等控制命令沿用编号和结果查询机制；不在断线期间自动排队执行这些操作。

## 4. 连接状态与自动恢复

连接状态：connecting（初次连接）、syncing（补齐中）、ready（已同步）、reconnecting（恢复中）、offline（网络不可用）、auth_required（需要登录）、forbidden（已失去权限）。同一房间页面同一时刻最多一个有效连接、一个连接尝试和一个重试定时器。

每次连接分配本地代次编号；离开页面、切房或启动新连接后，旧代次的消息、HTTP 响应和定时器不得修改当前页面。组件清理时取消监听、计时和未完成的连接准备请求。网络请求恢复晚于页面卸载时不得重新建立连接。

- 首次进入：获取新票据、建立连接、验证身份、加载一致快照、从快照 seq 补齐，再进入 ready。
- 短暂断线：保留已有状态，获取新票据重连，直接从最后连续应用的 seq 订阅；正常重连不重新下载整个房间。
- 重试间隔依次采用约 0.5、1、2、4、8、15 秒，并加入随机偏移，实际最大间隔 15 秒。网络恢复及页面回到前台时取消等待，立即进行一次连接健康检查或新连接尝试。
- 连接仍显示 OPEN（已打开）但超过接收期限没有服务器消息时，主动替换连接。页面回到前台先核对“最后收到消息的时间”，不能仅凭 OPEN 判断可用。
- 网络明确不可用时停止频繁重试；恢复事件触发重新检查。浏览器网络提示只作为触发信号，以实际请求和消息确认可达性。
- 身份过期停止盲目重试，引导登录；被踢或封禁结束订阅，显示无权限，保留可复制的本人草稿，停止自动补取。
- 连接建立、票据与快照等准备请求设置明确超时；同步连续 10 秒无进展时进入恢复流程，不能无限停在“同步中”。

## 5. 心跳、在线状态与代理

连接保活和玩家是否正在看页面分别处理：

| 项目 | 默认参数与行为 |
| --- | --- |
| WebSocket 协议心跳 | 服务端每 20 秒主动发送 ping（探测），监听 pong（回应）；60 秒没有有效回应或客户端消息才判连接失效 |
| 页面在线状态 | 前台每 30 秒上报一次，并在前后台切换时尽力上报；以用户多个设备聚合，任何前台有效设备都可标记在线 |
| 事件进度检查 | 服务端每 15 秒发送本房最新序号；有业务事件随时发送，不等定时周期 |
| 客户端失联检查 | 前台 45 秒没有任何服务器应用消息则主动恢复；前后台恢复时立即检查时间戳 |
| 代理超时 | 核对完整线上代理链，空闲超时至少覆盖 120 秒；已有更长配置可保留 |

浏览器协议层 pong 用于连接检测，不能据此宣称玩家正看页面。页面可能被系统暂停，允许连接随后重新建立；任何连接超时都不改变游戏生命周期。业务帧、进度帧均更新客户端最后接收时间。

服务端按房间批量读取最新序号，复用结果给本房连接，避免每个成员重复查同一个房间。权限校验保留，批量查询当前订阅的成员资格；踢人和封禁即时撤订阅，发送与补齐均受权限检查。异步巡检禁止重叠执行，同一订阅的补发按顺序执行，避免同时修改发送游标。

## 6. 事件补齐与快照边界

客户端只保存最后连续应用的 seq。重复事件忽略；出现缺口时保留当前页面、暂停应用缺口后的事件，启动一次补齐。并发到达的事件进入有上限的临时缓冲；补齐后按序合并，同一时刻只运行一个补齐过程。

服务端查询数据库持久事件，分批返回；达到本次订阅目标序号后发送 sync.ready（同步完成），其中 watermark（目标序号）必须与客户端连续进度核对。服务端“已发送到连接”的序号不能当成客户端“已应用”的序号。

游标超出保留范围、超过服务端进度、协议不兼容或缓冲超过 1,000 条时，返回明确的 resync_required（需要重新快照）。客户端在原画面上获取新快照并一次性替换服务端状态；草稿、待确认发送项、页签和阅读位置独立保存。

快照覆盖当前题目、成员、控制版本、已解锁提示、问答首屏、讨论首屏、续玩目标房间及历史分页游标。不能把讨论直接置空后跳到最新 seq，否则已经存在的讨论会从页面消失。快照与其 seq 来自同一数据库一致视图，之后补齐 seq 更大的事件。

## 7. 页面状态与提示

- 连接中断不清空记录、不返回首页、不以全屏加载替换已打开房间。初次进入且尚无数据时才显示整页加载。
- 短暂恢复在消息卡显示发送状态；重连超过 2 秒再出现轻量“正在恢复连接”提示。明确断网、需要登录或被踢立即显示对应提示；恢复后移除连接提示。
- 补齐期间可阅读、编辑草稿；待同步完成才开放新的游戏写入。错误提示区分消息发送失败、模型判断失败与连接恢复。
- 草稿及待确认发送项使用 IndexedDB（浏览器本地数据库），按账号、roomId、输入模式分开存储；刷新后可以恢复，退出账号清理该账号的草稿和待确认项。未保存成功必须提示，禁止声称已经保留。
- 已加载多人历史和连续 seq 在当前页面内存中成对保存；刷新后重新取快照，不能只恢复一个 seq 却缺少对应记录。
- 用户正在底部时跟随新消息；正在回看时保持锚定消息及偏移，显示“有新消息”。恢复和快照替换不触发全列表强制滚到底部。
- 切到新房时重新建立独立状态，旧房草稿不自动变成新房消息；旧房结束后的待确认项先查询原命令结果，明确未受理的内容停止重投。

## 9. 验收与体验目标

| 场景 | 通过条件 |
| --- | --- |
| 保存成功前延迟响应 | 只显示发送中；持久化证明到达后才显示已发送 |
| 保存成功但客户端丢失响应 | 查询或重投恢复同一条消息，数据库一条命令、一条问答或讨论，无重复消费 |
| 实时事件先于 HTTP 响应 | 本人占位卡合并一次，后来的响应不产生第二条 |
| 前台断网再恢复 | 历史、草稿与阅读位置保留；恢复后遗漏事件顺序一致 |
| 手机切后台、锁屏后回来 | 自动检查并重连，无需刷新；房间继续原题 |
| 连接表面打开但链路已断 | 接收超时触发主动恢复，避免长期无响应 |
| 切房或卸载期间旧请求返回 | 不改新房状态、不建立遗留连接、不产生重复定时器 |
| 补齐期间继续有新消息 | 连续 seq 无缺口、重复不追加、旧房任务不串到新房 |
| 游标过期与快照替换 | 明确重新同步；讨论、续玩入口恢复，草稿和回看位置保留 |
| 被踢、封禁、登录过期 | 停止相应订阅及无效重试，提示准确，禁止继续取得事件 |
| 服务进程重启 | 重连并从数据库补齐；消息与权益各执行一次 |

目标：点击发送后的本地状态反馈在 100ms 内；健康网络下服务端受理第 95 百分位不超过 500ms（不含模型执行）；网络可达且浏览器已恢复执行后，1,000 条以内遗漏事件恢复第 95 百分位不超过 3 秒。通过真实浏览器、真实 PostgreSQL、真实网络断开与进程重启验证；报告硬件、并发人数及测量起止点。心跳流量、数据库查询量和恢复次数一并测量。

实施顺序：C01～C02 可靠发送，C03～C05 连接与补齐，C06 页面体验，C07～C08 服务效率与观测，最后完成上述验收。人工体验确认后再提交代码。
